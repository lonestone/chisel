# Issue tracker

**Mode: local markdown.** Work is tracked as task files in this repo — there is
no external tracker wired up for now.

- **Active tasks:** `doc/project-management/tasks/<time-id>-<intention>.md`
  where `<time-id>` is generated by `scripts/task-id.sh` (`YYYYMMDD-HHmm`, for
  automatic chronological sorting). Large tasks may be split into slice files
  under `tasks/<time-id>-<feature-slug>/<NN>-<slice-slug>.md`, numbered in
  dependency order (see the `slice-task` skill)
- **Completed tasks:** moved to `doc/project-management/archive/`
- **Format:** the template in `doc/project-management/000-task-file-template.md`
  (reading-gradient zones: 🧑 review carefully / 🧑 review if relevant / 🤖 agent zone)
- **Status:** the `**Status:**` field in each task file (🔴 🟡 🟠 🟢 ⚪ ⚫)
- **Work the frontier:** any task/slice whose blockers are all done can start

## Switching to an external tracker later

To move to Linear (or GitHub Issues), rewrite this file with the new workflow
(how to fetch a ticket, how to publish, which labels). The skills and rules
read this file — nothing else needs to change. When an external tracker owns
the business spec, the agent must check the ticket for updates before working
on a task derived from it.
