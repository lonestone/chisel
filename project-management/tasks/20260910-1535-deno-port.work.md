## Program Design

### Module layout under `src/`

The entry `deno.json` names is `src/main.ts`. One module per concern, each
importable on its own so a test can exercise it through the CLI seam without
reaching inside it:

| Module | What it decides |
|---|---|
| `src/main.ts` | Argument parsing, usage text, dispatch, exit codes (0 / 1 / 2). The only module that calls `Deno.exit`. |
| `src/paths.ts` | Package-root resolution from `import.meta`, the socle paths derived from it, reading a packaged file, the package version out of `deno.json`. |
| `src/socle-files.ts` | The list of socle files that ship with the package, relative to `socle/`. Data, no logic. |
| `src/hash.ts` | SHA-256 (lowercase hex) of bytes and of a file; the managed-block hash of an `AGENTS.md`. |
| `src/manifest.ts` | Read / write `.agents/.chisel.json`; the managed-file list; the old-vs-new diff that implements the orphan rule. |
| `src/install.ts` | Copying the managed set into a target, the foreign-skill warning, the `.claude/skills` link, `AGENTS.md` and `CLAUDE.md`, the journal skeleton. |
| `src/render.ts` | Profile frontmatter and body, the two agent-definition renders, writing over a definition chisel owns. |
| `src/glue.ts` | The structured parser of `.agents/project.md`: lettered sections, subsections, list items. Pure — it never touches the disk. |
| `src/project-md.ts` | The three glue operations: write it once, tick §E, retarget §A, and find the stale subsection. Every one of them goes through `src/glue.ts`. |
| `src/report.ts` | The report lines and the `chisel:` / `chisel: warning:` prefixes, so a line's wording lives in one place. |
| `src/init.ts`, `src/update.ts`, `src/check.ts` | One command each, returning an exit code rather than exiting. |

Every test runs the CLI as a real subprocess —
`new Deno.Command(Deno.execPath(), { args: ["run", "-A", entry, ...] })` — so
exit code, stdout and stderr are the ones a user gets, not a return value an
in-process call happens to produce.

### How the package root is resolved, and how the socle ships

`src/paths.ts` computes `new URL("../", import.meta.url)`: the parent of the
directory holding the entry module, whatever the working directory. For a
`file:` URL the directory is then passed through `Deno.realPath` when that
succeeds, which is what makes a package reached through a symlinked directory
resolve to its own socle — the analogue of the bash `readlink` loop, and the
case the `symlink` group protects. Deno does **not** canonicalise the main
module: a symlink to a single module file cannot even load its own sibling
imports (proved in Notes & Snippets), so the carrier of that group is a
symlinked package *directory*, which is what a real installation looks like.

Reading a packaged file goes through one function, `readPackageFile`, which
resolves the relative path against the package root URL and then reads it
with `Deno.readFile` for `file:` URLs and `fetch` for anything else — the
JSR-cache case, where the module's own URL is remote and the socle files are
served beside it.

An HTTP origin has no directory listing, so the socle cannot be discovered by
walking it once the package is remote. The list of files that ship therefore
lives in `src/socle-files.ts`, committed, sorted, and used for two things at
once: copying the managed set into a target, and deriving the managed-file
list of the manifest (the same discipline the bash file states — chisel
manages exactly what it copied). A list that drifts from the tree would
silently stop shipping a file, so `test/integrity.test.ts` compares it to a
real walk of `socle/`.

### The manifest diff that implements the orphan rule

`writeManifest` rewrites `.agents/.chisel.json` as `{version, managed}` with
`managed` mapping each relative path to its SHA-256, plus the pseudo-entry
`AGENTS.md#block` for the managed block. Keys sorted, two-space indent, one
trailing newline — byte-identical to what the python writer produced.

`update` reads the manifest **before** it copies anything, then compares:

```
old = managed map read from the manifest on disk (may be empty)
new = managed map written by this run
for name in sorted(old) - sorted(new), name != "AGENTS.md#block":
    if the file is absent           -> nothing to say, it is already gone
    elif sha256(file) == old[name]  -> delete it, report "  removed: <name>"
    else                            -> keep it, report "  orphaned: <name>"
                                       plus a warning naming it on stderr
```

The hash comparison is the whole point: a file whose content still matches
what chisel last installed carries nothing of the project's, so removing it
loses nothing; a file that changed since may carry someone's edit, so it stays
and is named. `AGENTS.md#block` is excluded because it is not a file.

`(no managed files changed)` is printed only when this run reported no
`changed:`, no `removed:` and no `orphaned:` line — otherwise the summary
would contradict the lines above it.

The foreign-skill warning loses the words "never tracked": with orphans
handled, a file chisel installed and later retired is removed or named, so the
only directories the warning fires on are genuinely foreign ones, and what is
true of those is that chisel neither updates nor manages them.

### The glue parser and its call sites

`src/glue.ts` exports `parseGlue(text)`, returning the document's lines plus
its lettered sections: for each one its letter, its title, the line it starts
on, its list items (checkbox state, label taken from a backticked or bold
lead, value, line number) and its subsections (`### B1 · …`) with their own
items. Nothing in it matches a template sentence: a section is found by its
letter, an item by its label.

Three call sites, all in `src/project-md.ts`:

1. `tickAdapterInventory` — section `E`, one item per adapter, ticked when
   that adapter is actually in place. Only on a glue the current `init` run
   created.
2. `pointNewGlueAtExistingJournal` — section `A`, the item labelled
   `Changelog`, rewritten only while it still holds the template's default
   path. Only on a glue the current `init` run created.
3. `findStaleSubsection` — the `B3` subsection of section `B`, reported by
   `update` and `check` on a `stale:` line, never edited.

### Report lines and exit codes

Same lines as the bash CLI on every path the bash suite pins, with three
additions: `removed:` and `orphaned:` on `update`, and `stale:` on `update`
and `check`. Usage errors — an unknown command, an extra positional argument
— name the offending argument on stderr, print the usage, and exit 2. `--help`
exits 0 and names the commands, the exit codes, the Deno prerequisite and the
permissions the CLI needs. A fatal error keeps the `chisel: ` prefix and exit
1; `check` keeps exit 1 for divergence. The `stale:` line does not change an
exit code: the glue is the project's file, and a residue in it is not a
divergence of a managed file.

## Notes & Snippets

**Deno does not canonicalise the main module.** A symlink pointing at a
single module file cannot even load its own siblings:

```
$ ln -s <repo>/src/main.ts <linkdir>/chisel.ts && deno run -A <linkdir>/chisel.ts
error: Module not found "file://<linkdir>/dep.ts"
```

So the `symlink` group's carrier is a symlinked package **directory**, and
`src/paths.ts` still passes the resolved root through `Deno.realPath` — a
symlinked directory resolves to the real package, which is the property the
group protects.

**`deno x` with a `jsr:` specifier, what could be verified here.**
`deno x --help` says, verbatim, "Execute a binary from npm or jsr, like npx",
and documents `--install-alias [<VALUE>]` as "Creates a dx alias so you can
run dx <command> instead of deno x <command>". So the invocation form and the
`dx` alias in the README are read off the tool itself. What only publication
will prove: that JSR serves the packaged `socle/` files beside the module (so
`readPackageFile`'s `fetch` branch finds them), and that the permission
prompts a first run raises are the ones the help text announces. Nothing
local can settle either — both need a published version.

**Byte-for-byte details of the manifest.** Python's
`json.dump(..., indent=2, sort_keys=True)` and `JSON.stringify(obj, null, 2)`
agree on this shape once the keys are sorted by hand; the file ends with one
newline.

**The render goldens are hand-authored.** `test/fixtures/render-golden/` will
hold a profile and the two renders expected of it, both written by hand from
the render contract (frontmatter with the two quoted, escaped fields; the
provenance comment; the body verbatim after a blank line — and for Codex, a
comment line, the two fields, then the body inside a multi-line literal
string). They are the oracle precisely because no code generated them.

## Findings

Every judgement call this chantier needed, and what it decided. — mason,
2026-09-10.

1. **The `stale:` line does not change an exit code.** The spec asks `update`
   and `check` to report a glue that still carries the `B3 · Autonomous runs`
   subsection, and never to edit it. It does not say whether `check` should
   then fail. It reports, and exits as it would have: the glue belongs to the
   project, a residue in it is not a divergence of a managed file, and a
   `check` that could only be made clean by hand-editing a file chisel
   refuses to touch would be a trap. `clean — no divergence` still prints
   beside a `stale:` line, and means what it says — no managed file diverged.

2. **An orphan that is already gone is not reported.** The orphan rule
   compares the old manifest to the new one. A file that left the managed set
   *and* is absent from disk needs neither a deletion nor a warning, so it
   produces no line at all. Only a file that is still there is removed
   (content unchanged) or named (content changed).

3. **`(no managed files changed)` covers the orphan lines too.** The bash
   printed it whenever no `changed:` line appeared. It would now be able to
   print under a `removed:` line and contradict it, so it prints only when
   this run reported nothing at all.

4. **The `symlink` group changed carrier, and says so.** Deno resolves a
   symlinked main module without canonicalising it, so a link to
   `src/main.ts` alone cannot load its own imports — the bash shape of that
   test is not expressible. The Deno test links the package *directory*,
   which is what `deno install` and a checkout-plus-symlink actually produce,
   and the resolution still goes through `Deno.realPath`. Rows 50–51 of the
   parity table carry the renaming and the date.

5. **The line-count assertion is dropped, not renamed.** Row 94 was the
   runner asserting the suite's own length against 600. The chantier removes
   invented numeric limits, so nothing replaces it: `test/TESTS.md` states the
   behaviour-only rule and the groups table, and no test counts lines.

6. **The socle ships as a committed file list.** An HTTP origin has no
   directory listing, so once the package is remote the socle cannot be
   discovered by walking. `src/socle-files.ts` is that list, and
   `test/integrity.test.ts` compares it to a walk of `socle/` so it cannot
   drift — the failure mode of a hand-kept list is a file that silently stops
   shipping, and that test is what closes it.

7. **Two before-values in the spec's criteria differ from what HEAD
   measures.** `grep -rn "python3" src test deno.json README.md` matches 3
   lines today, not 5 (the 5 counts occurrences inside `bin/chisel.sh`); and
   `grep -rn "npx @lonestone/chisel" README.md socle/` matches 6 lines, not 5
   (five in the two skills, one in the README — the criterion's own list of
   files names both). Both after-values are 0, so no criterion is weakened;
   the numbers in the table above are the ones this session measured, with
   the commands beside them.

8. **`PHILOSOPHY.md` makes no claim this chantier falsifies.** It was not
   opened for editing; it was searched for what the port could contradict —
   any mention of npm, npx, node, bash or python, of an installation command,
   and of the suite's retired numeric budgets ("600", "assertion",
   "scenario"). None of those appear in it. The spec asked for a report
   either way.

9. **The `.DS_Store` at the root of `socle/` never shipped and still does
   not.** The bash copied three named directories and six named files, so it
   was never in the installed tree; the committed socle list is built the
   same way and excludes it. Worth knowing that the file is in the repo at
   all.

10. **One commit in the range is not this chantier's.** `git log
    b0b391f..HEAD` lists `c8b68a2`, "Record the fast-track extension to the
    Deno port chantier", which added eight lines to
    `project-management/review-360-decisions.md` at 15:38 on 2026-09-10 —
    before this session's first commit and by the repo's owner, not by the
    Mason. No commit of this chantier touches that file
    (`git log 38e3464..HEAD -- project-management/review-360-decisions.md` is
    empty). It is in the diff range only because it sits between the spec's
    commit and this work; the "nothing else moved" criterion should be read
    against the nine commits listed in the worklog.

11. **`deno fmt` was scoped after it reformatted the whole repo.** Run with no
    configuration it rewrapped every markdown file, this task's own spec
    included. That was reverted with `git checkout` and `deno.json` now scopes
    `fmt` and `lint` to `src/` and `test/`, excluding `test/fixtures/` (the
    oracle) and `test/TESTS.md` (prose a formatter should not rewrap). Worth a
    reviewer's eye: `deno task check` therefore proves nothing about markdown,
    by design.

12. **The `render` group gained a check the bash suite could not make.** The
    codex render is now parsed back with `@std/toml` and its
    `developer_instructions` compared to the profile body — so an escaping
    bug in a description or a delimiter in a body fails the suite instead of
    producing a file that merely looks right.

13. **`init` on a directory that is not a repo still works, as before.** The
    journal case (b) builds a bare directory with only a
    `project-management/CHANGELOG.md` in it, because that is the smallest
    shape that exercises the guard. Neither the bash CLI nor this port asks
    whether the target is a git repository, and this chantier did not change
    that.

14. **A skill retired upstream was called a stranger's, twice over.** The
    Foreman reproduced it: `init` on the brownfield fixture, a
    `.agents/skills/retired/SKILL.md` recorded in the manifest with its true
    hash the way an older chisel would have recorded it, then `update`. The
    run printed `.agents/skills/retired was not installed by chisel` and, on
    the next line, `removed: .agents/skills/retired/SKILL.md` — a warning
    contradicted by the very report it preceded. Then the emptied directory
    stayed, so every later `update` and `init` repeated the claim forever.

    Two causes, two changes. The warning ran inside `copyManagedFiles`,
    before the orphan pass, and asked only the shipped socle list — which by
    construction cannot know what an older socle installed. It now takes the
    previous manifest's names as an argument and treats any skill directory
    that manifest tracked as chisel's own; `copyManagedFiles` no longer calls
    it at all, since deciding what is foreign is not part of copying. `init`
    reads the manifest before writing and passes it; `update` passes it and
    calls the warning *after* the orphan pass, so the tree it inspects is the
    one that remains. A genuinely foreign directory still gets the warning
    from both commands — the guards test pins `update`, and the case was
    re-run by hand for `init`.

    Second, `update` now takes an emptied parent directory away with the
    orphan that emptied it (`removeEmptyParents`), walking up and stopping at
    the first directory chisel creates itself — `.agents`, the three trees
    under it, the two agent directories, `project-management`, `scripts`.
    Those stay whether or not they still hold anything: an update that
    retired a file has not un-installed the socle. A directory holding
    anything else — a file of the project's, a dotfile — stays too, and so
    does everything above it.

    Judgement calls. The filter is by top-level skill *name*, not by exact
    file: a retired skill's directory may hold several files and a `README`
    the manifest never tracked, and warning about the directory because one
    of its files was untracked would reproduce the same lie in miniature.
    The previous-manifest filter is kept even though placing the warning
    after the orphan pass would cover the `removed:` case on its own —
    because the `orphaned:` case does not: a retired skill the project has
    since edited is kept on disk, and only the manifest can say it was
    chisel's. And the two orphan tests were extended rather than joined by a
    third: the retired formula they already used sits directly under a
    managed root, the retired skill sits one level deeper, and the pair in
    one test is what proves the walk stops in the right place. — mason,
    2026-09-10.
