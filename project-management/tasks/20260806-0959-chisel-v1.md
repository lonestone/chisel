## Context

The fused task methodology (Lonestone lifecycle × Pocock skills, reading
gradient, seams, think/type split) is proven on two pilots (music-downloader,
evea-ai) but lives as hand-copied files. Chisel bundles it into a git repo
installable in any project via `npx @lonestone/chisel init`, with a per-repo
setup questionnaire and a controlled upstream-sync path for the Pocock forks.

Decisions were grilled on 2026-08-06 (see Notes for the full decision log).

## Scope

**Included:**
- The `chisel` repo as the canonical source of the socle (skills, rules,
  workflows/methodology docs, task template, `task-id.sh`)
- Unified **`.agents/` layout** in equipped projects (Codex + Cursor native;
  one `.claude/skills` symlink for Claude Code; `AGENTS.md` source of truth,
  `CLAUDE.md` = `@AGENTS.md` import)
- **`npx @lonestone/chisel`** CLI (sh script behind an npm bin):
  `init` · `update` · `check` — editable copy, managed blocks, glue never touched
- **Setup questionnaire** (prompt-driven skill): sections A–G → writes
  `.agents/project.md` (the glue) — task workspace, tracker, minimal reading
  list, living docs, tools, gate commands, domain memory
- **Genericized rules/skills**: no hardcoded project paths — everything
  resolves through `project.md`
- **Upstream sync**: per-skill frontmatter (`x-upstream`) + `upstream.lock.json`
  + a `sync-upstream` skill (agent proposes, human validates; ~2–6×/year)
- **Migration of the two pilots** to the installed layout

**Not Included:**
- Plane MCP configuration (the setup may point to it, never configures it)
- Claude Code plugin/marketplace channel (possible later, passive consumers)
- An umbrella "agents" repo (one coherent thing = one repo)
- Renaming `crucible` (separate chore)
- Boilerplate integration beyond detection (the boilerplate adds chisel to its
  own setup on its side)

## Acceptance Criteria

- [ ] On a fresh boilerplate project: `npx @lonestone/chisel init` + the
      questionnaire produce a working `.agents/` layout; a fresh agent session
      then routes correctly (ambient → task creation → work) without any
      hand-fixing
- [ ] On a non-boilerplate (brownfield) repo: init completes, questionnaire
      scans and assists building the minimal reading list
- [ ] `update` re-renders managed parts and provably never touches
      `project.md` nor project-owned files
- [ ] `sync-upstream --check` lists upstream drift without writing; a full run
      produces reviewable diffs only (nothing auto-applied)
- [ ] Both pilots migrated and working (their existing tasks/changelog intact)
- [ ] Cursor reliability verified: task rules applied from `AGENTS.md` alone,
      or the `.mdc` shim fallback is activated and documented

## Seams

- **The CLI** (`chisel init|update|check`): black-box tested on fixture repos
  (boilerplate-shaped, brownfield-shaped) — file tree in, file tree out
- **The generated `.agents/` layout**: the contract every tool reads; asserted
  as a whole after init
- **`project.md`**: the single indirection point — rules/skills resolve paths
  through it, tests assert no hardcoded path remains in the socle

## Architecture

Two artifacts: the **chisel repo** (source) and the **equipped project**
(target). `init` copies + renders; `update` re-renders managed parts only.

```
chisel repo (source)                     equipped project (target)
├── package.json  @lonestone/chisel      ├── AGENTS.md          ← managed block
├── bin/chisel.sh  (init|update|check)   ├── CLAUDE.md          ← "@AGENTS.md"
├── socle/                               ├── .claude/skills → .agents/skills
│   ├── agents/                          ├── .agents/           ← THE folder
│   │   ├── skills/      (15 forks)  ──▶ │   ├── skills/
│   │   ├── rules/       (task-*.md) ──▶ │   ├── rules/
│   │   ├── workflows.md · methodology.md│   ├── workflows.md · methodology.md
│   │   └── project.md.tpl           ──▶ │   └── project.md     ← GLUE (setup Q&A,
│   ├── templates/ (AGENTS block,        │                         never updated)
│   │   task template)               ──▶ ├── project-management/ ← tasks/archive/
│   └── scripts/task-id.sh           ──▶ │      CHANGELOG (root, per decision A)
├── upstream.lock.json  (Pocock SHAs)    └── scripts/task-id.sh
└── project-management/  (dogfood)
```

Install flow: `init` → explore repo (boilerplate? existing CLAUDE/AGENTS?
scripts?) → questionnaire A–G (prefilled) → write glue + copy socle + render
adapters → verify (`check`).

## Implementation Decisions

Cross-slice only (per-slice design lands in each slice's Design section at its
plan gate):

- **sh over Node** for the CLI: no runtime deps, npm is only the distribution
  channel (`bin` → `chisel.sh`)
- **Managed blocks** delimited by `<!-- chisel:begin -->` / `<!-- chisel:end -->`
  markers in AGENTS.md; everything outside is project-owned
- **Glue = runtime indirection** (`project.md`), never template-rendering of
  paths into rules — rules stay byte-identical across projects, so `update`
  never conflicts
- **Questionnaire defaults** (grilled 2026-08-06): tasks at root
  `/project-management/`; tracker local (options GitHub, Plane); reading list
  prefilled from boilerplate (`apps/documentation` = THE doc reference, split
  abandoned); glossary + decisions in `apps/documentation` for boilerplate
  (root `CONTEXT.md` + `docs/adr/` otherwise); decisions link into existing
  architecture pages rather than duplicating rationale
- **Upstream**: `x-upstream: {repo, path, sha, changes}` frontmatter per
  forked skill; central lock keeps SHAs only; a skill too diverged gets
  `upstream: none` (planned state, not a failure)

## Testing Strategy

- Fixture repos (mini boilerplate-shaped + brownfield-shaped) committed under
  `test/fixtures/`; init/update/check run against them (bats or plain sh
  asserts) — behavior through the CLI seam only
- Idempotence: `init` twice = no diff; `update` after glue edit = glue intact
- Prior art: Pocock's `setup-matt-pocock-skills` (prompt-driven flow),
  `link-skills.sh` (symlinks)
